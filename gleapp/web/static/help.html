GLEAPP — Graphics · Logs · Examination · Automated Processing · Parsing. A fully offline image and video triage tool for digital forensic examiners. It ingests media, hashes and de-duplicates it, decodes formats a browser can't, screens for faces and skin tone, matches against known-hash lists, and gives you a fast keyboard-driven review gallery with a locked Project VIC category scheme.

GLEAPP ships no hash database of illegal content and performs no content classification. Face detection and skin-tone ratio are investigative signals only. Every category decision is the examiner's.

1. Getting started

On launch with no case open, GLEAPP shows the launcher. The ? Help / Manual button (top-right of the launcher, and in every case's header) opens this manual.

  • Recent cases — click to reopen. Only cases that contain files are listed; each shows its live file count.
  • Open existing case — point at a folder that contains a case.gleapp file.
  • New case — give it a name, a folder (created if missing), and your examiner name, then add one or more evidence sources with the buttons under Evidence to ingest (or paste a path and click Add):
    • Browse for folder — scanned recursively for media;
    • Browse for extraction or acquisition — a full file-system extraction archive (.zip, or a .tar plain or compressed: .gz, .bz2, .xz); its media is read straight from the archive unless you tick Copy media out of extraction archives, and a compressed tar is always copied out. Or an E01 acquisition (.E01 with its numbered segments beside it), whose filesystems are walked file by file so each file keeps the name, path and dates the filesystem recorded: ext2, ext3, ext4, FAT32, exFAT, NTFS, HFS+, HFSX, APFS, QNX4, QNX EFS, QNX ETFS and QNX IFS. A volume that cannot be read is named in the Source panel afterwards. Carving the free space for deleted media is a separate step, asked for after ingest;
    • Browse for JSON — a GLEAPP job spec (named sources) or a Project VIC 2.0 (US) JSON, detected automatically; the VIC media folder is resolved next to the file, and existing MediaID / category / original path / MIME / victim-offender flags are imported.

Ingest options: Face / skin screening (on by default; can be run later instead), video key frames per clip (default 6), and Copy media out of extraction archives into the case (off = the case stays small but the archive must stay put; on = the case is self-contained). Click Create case & ingest.

The gallery opens as soon as files are registered — you don't wait for processing to finish. A progress bar along the bottom of the window shows the running count and stage; thumbnails fill in as each file is processed and the file count climbs. You can review, categorize and tag any already-processed file while the rest catch up. Duplicate-stacking, known-hash matching and clustering run in the final stage, so those columns and filters settle a moment after the last thumbnail. The bar clears itself when processing finishes; closing the case is blocked until then.

2. The case

One case is one folder. Inside it:

case.gleappthe SQLite database — everything GLEAPP learns about a file lives here, so runs are resumable
thumbs/generated grid thumbnails and video key frames
views/full-size JPEGs transcoded from formats the browser can't show (HEIC, TIFF, KTX…)
extracted/media unpacked from container files (Snapchat LZC bundles)
reports/exported reports, CSV/JSON, MD5 lists, KMZ, Project VIC exports, LAVA projects
backups/timestamped snapshot copies of case.gleapp

Switch cases with ⇤ Close case (snapshots first, returns to the launcher). The original evidence is never modified — GLEAPP reads it and writes only inside the case folder.

3. The review gallery

Left: the filter sidebar. Centre: the grid or details list (switch with the ▦ Grid / ☰ List toggle), with a control bar across the top (view toggle, Columns, Sort, thumbnails Per page, Tile size, Times timezone, and the shortcut legend) and pagination above and below. Right: the details pane (toggle with I or the "Details pane" button; its state is remembered).

The filter sidebar, selection, categorize shortcuts, right-click menu, details pane and pagination all work the same in either view.

Details list view

☰ List shows one row per file with a column for every stored detail — built for triage by metadata rather than by eye.

  • Sort — click a column header; click again to reverse (an arrow marks the active column).
  • Filter — type in the box under a header. Filters run server-side across the whole result set, not just the visible page:
    • text columns — case-insensitive substring; none = blank, set = non-blank. Name and File path match what's shown, including the on-disk name / path used as a fallback when a file has no original name or VIC path.
    • number columns — 500, >=500, >500, <=500, <500, or a range 100-500 / 100 .. 500. none / set also work.
    • Size — a bare number is KB and means “that size or larger”; use a unit otherwise: >1mb, 100kb-2mb, 2gb.
    • Skin ratio — a bare number is a percent, “that or higher” (30 = ≥ 30 %); 10-50 works too.
    • Duration — m:ss or bare seconds, meaning “that long or longer”: 0:30, >1:00, 1:00-5:00.
    • GPS lat / lon — a bare number is a partial match (45 finds 45.4215); >40, -80 .. -70, set / none also work.
    • date/time columns (FS created, FS written, FS accessed, Ingested) — two calendar pickers, from and to; fill either or both. Day boundaries follow the toolbar Times timezone, so the range matches the dates shown in the column. Captured (EXIF) is text — filter it as a substring (2024-06).
    • enum columns (Type, Source, Category, Hash kind) — pick from the dropdown.
  • Resize — drag the right border of a column header to widen or narrow it (overflow is clipped with an ellipsis; hover the cell for the full value). Double-click the border to reset that column.
  • Clear column filters — toolbar button (with the active filter count) that drops every column filter at once; sort and column choices stay. The sidebar Clear filters clears these as well.
  • Columns ▾ — choose visible columns; All / Defaults presets, plus Reset widths.
  • View, visible columns, column widths, sort and column filters are remembered per browser.

Paths: the File path column shows the original path recorded in the Project VIC JSON (MediaFiles.FilePath) — where the file lived on the source device. For a folder-ingest case (no VIC data) it falls back to the file's path on disk. File path (working copy) always shows where GLEAPP resolved the file on your machine; add it from Columns ▾ if you need it.

Four distinct kinds of date — GLEAPP keeps them separate:

Captured (EXIF)when the media records it was taken — EXIF DateTimeOriginal / embedded metadata only; blank if the file has none.
FS createdfilesystem creation time — os.stat on a folder scan, or MediaFiles.Created from a Project VIC import.
FS writtenfilesystem last-modified time — stat mtime, or VIC MediaFiles.Written.
FS accessedfilesystem last-access time — stat atime, or VIC MediaFiles.Accessed.

A filesystem timestamp is not a capture time; GLEAPP never fills "Captured" from one. All four show in the details pane, the list view and as report fields.

Timezone. Filesystem and ingest times are stored in UTC. The Times selector in the control bar shows them in a timezone you pick — a shortlist, your device's zone, or any IANA name via Other… — with daylight saving applied automatically. The choice is saved per case and as your default for new cases, and is stamped into the report header. It never changes Captured (EXIF) — that is the camera's own local wall-clock time, always shown exactly as recorded.

Header buttons: Close case, ⚙ Categories, Details pane, Snapshots, Hash stash, Export Project VIC (shown for VIC cases), Export report, and ↻ Refresh — which re-runs the current filter so files that no longer match it (e.g. ones you just categorized) drop out of view.

? Help ▾ opens a small menu with two entries:

  • Manual — this document.
  • Processing history — the case processing log: every ingest, process, screening, hash-set match, carve and examiner edit run against this case, newest first. A process run lists each stage — media processing, known-hash match, exact stacking, visual stacking, near-duplicate clustering — with a ✓ or ✗ for whether it succeeded, so a stage that failed does not hide the ones that worked. The "Show" menu narrows the list to runs, examiner edits, or only runs with a failed stage. This is the same audit log written into the LAVA export.

4. Tiles & badges

Each tile shows the thumbnail, the file name, a coloured bar along the bottom with its category name (grey "Uncategorized" if none), and small badges. The name shown is the original file name where it is known (e.g. from a Project VIC import, where files are stored on disk under their MD5); hover for the full name. The same rule applies to the list view's Name column and the report; the stored (MD5) name is still available as Stored name.

The file name and category color bar sit below the thumbnail, never over it, and the thumbnail always shows the whole image (never cropped) — important when text is burned into the top or bottom of a screenshot or Snap. Small corner badges still sit over the image corners; the full-size viewer shows the complete image with nothing over it.

NSRLmatched a known-good set (the badge shows the set's first word). NSRL matches are auto-categorized Non-pertinent if still uncategorized
STASHmatched your local hash stash — a file you categorized 1–3 in another case. Adopts that category if still uncategorized

Video tiles show a duration label and a play glyph; hover and move the cursor left-to-right across a video tile to scrub through its key frames.

Single-click selects. Double-click opens the full-size viewer (video plays with controls; non-web image formats are transcoded on the fly). Right-click for a context menu (find similar, details, view full size, categorize, tag, export MD5s, open the original file).

In the full-size viewer, Lighten dark areas (top-left) applies an adjustable shadow lift for checking content in badly underexposed photos. It is a view-only display filter — the file, its thumbnail and its hashes are never changed; only the on/off and strength setting is remembered (per browser). Exported reports show the original image, not the lightened view.

6. The details pane

Click a tile with the pane open (I) and it fills with: a preview and "View full size" button; the current category and the category buttons; Find similar; Add tag; Hex view (H, or right-click → Hex view) — a scrolling offset / hex / ASCII dump of the raw file, page through it or type an offset (decimal, or 0x-prefixed); existing tags (click × to remove); a video key-frame filmstrip; a metadata table (source, type, original name/path, MIME, VIC MediaID and flags, size, dimensions, duration, captured date, camera, faces, skin ratio, known-hash, exact/visual/near-dup group sizes, error); GPS with a Copy button and, once a basemap is imported (section 19), an offline map of the spot; MD5 / SHA-1 / SHA-256 / pHash; a Notes box that autosaves as you type; and filmstrips of the file's exact copies and visually-similar files (click one to jump to it; "Show only this group" filters to the visual-match set).

7. Categories — the mandatory Project VIC scheme

Every case is seeded with codes 0–5, the Project VIC 2.0 (US) category scheme. They are locked: they cannot be renamed, recoloured, reordered, hidden or deleted (in the ⚙ Categories editor they show read-only with a 🔒). Number keys map to them: 1–5, and 0 clears a category.

CodeNameWhat it is for
0Uncategorized Not yet reviewed — no decision made. The default state and the backlog you work down. Filter to it and categorize each file; the cursor advances to the next one automatically, and ↻ Refresh clears the done ones from view.
1CAM (Child Abuse Material) Depicts a real prepubescent child, or a minor who has not obviously reached puberty, engaged in a sexual act; the lascivious exhibition of the genitals or pubic area; or sadistic/masochistic abuse of a minor. The most serious category — illegal contraband. Notable / evidential in reports.
2Child Exploitative / Age Difficult A sexualized depiction of a minor that does not meet the Category 1 threshold (e.g. non-penetrative sexual posing, sexualized "child erotica", a pubescent minor), or a person whose age is genuinely difficult to determine and could be a minor. Notable.
3CGI / Animation (Child Exploitative) Computer-generated imagery, drawings, cartoons, anime or rendered art depicting Category 1 or 2 content. Not a real child, but still exploitative material. Notable.
4Comparison Images (Non-pertinent) Images kept for comparison or identification purposes — known-series reference images, images used to identify a victim, location or offender — that are themselves non-pertinent to the primary offense. Also for non-pertinent images an examiner wants to keep specifically flagged. Not notable.
5Non-pertinent Everything else — not child-exploitation material and of no evidentiary value for this offense: family photos, memes, screenshots, app assets, OS and application files. Not notable. An NSRL known-good hash hit auto-categorizes an uncategorized file here.

Adding your own: the ⚙ Categories editor's "+ Add category" creates code 6 and up. Your categories are fully editable — rename, recolor (click the color swatch next to the name), delete (soft-deleted while in use so labels are kept), drag to reorder (they always sort after the presets). They get number-key shortcuts 6, 7, … in order and start with an auto-assigned color.

Categorizing is non-destructive to the evidence and is recorded in the case audit log with your examiner name. Codes map 1:1 to Project VIC codes on export; code 0 exports as null.

8. Filtering — every option

Filters combine with AND and apply as you change them. The top of the sidebar is always visible — Search, Category, Type, Source — and below it is one collapsible section per feature (Known hashes, Faces & skin, Duplicates, Errors, Location); each section holds its filter controls and its buttons (import, re-check, screen, retry, re-scan). A section with an active filter shows a dot on its header — so you see what's applied even when it's collapsed — and each section remembers whether you left it open. The top also shows a filter count with Clear; the header stat line shows how many files match.

Search

Free text. Every whitespace-separated word must match somewhere (AND); within a word it matches across all of: relative path, absolute path, original device name and path, camera, notes, MIME, source, capture date, examiner, known-hash name, error text, MD5 / SHA-1 / SHA-256 / pHash (partial hashes work), and tags. So dcim 2024-07 finds files whose path mentions DCIM and whose date is in July 2024.

Category / Type / Source

  • Category — Any, a specific category (presets and your own, hidden ones marked), or Uncategorized, which enables the auto-advance review flow.
  • Type — image, video, or other (not decodable media — archives, documents, unknown formats).
  • Source — restrict to one ingest source (folder name, or the Project VIC source).

Known hashes

  • Show — all files (default), any imported hash set, or only one named set (e.g. one CyberTip). Filters to the files that set flagged.
  • Any known-hash hit — matched any hash set, including the global store (NSRL) and the local hash stash.
  • Hide known-NSRL — hides every file that matched a known-good set (NSRL etc.), so OS and app files stop cluttering the review. The count beside it is how many are hidden.
  • Import hash set… / Re-check, the imported-set list, and the Reference data and hash stash lines — see section 11.

Faces & skin

  • Has faces — faces > 0 from YuNet. Needs screening to have run.
  • Skin-tone ratio — Any, or 10 % / 30 % / 50 % or more of the frame skin-toned. Needs screening.
  • Run face / skin screening — runs it now if it hasn't.

Duplicates

  • Show — only files that have a relative in the collection:
    Has any duplicatein a ≥2 exact stack, a visual stack, or a near-dup cluster
    Has an exact copya byte-identical twin exists (same MD5)
    Has a visual copythe same picture, re-encoded or resized
    In a near-dup clusterburst shots, crops, filtered/annotated versions, video frame grabs
  • Collapse duplicates & visual matches (on by default) — one tile per visual group. The representative is chosen from files that match your other filters, so a group still appears when only a non-head member carries the attribute you filtered on. Counts reflect groups, not individual files.
  • Re-scan for duplicates — rebuild the exact / visual / near-dup groupings without a full reprocess (use after importing, or on an older case).

Errors

  • Processing error / no preview — files that failed to decode (the count is on the section header). Retry failed files re-runs processing on just those.

Location

  • Has GPS — has latitude/longitude in its metadata.

Sort

Path, capture date, size, skin ratio (desc), faces (desc), or cluster. "Thumbnails per page" (50–1500) and "Tile size" are remembered between sessions.

9. Duplicates & similarity

GLEAPP builds three levels of grouping during processing, strongest to loosest:

LevelMeaningHow it's decided
Exact stackidentical filesame SHA-256 (or MD5)
Visual stackthe same picture, re-saved / resizedperceptual hash within ~6 bits, cross-checked against dHash
Near-dup clusterthe same scene / subject — bursts, crops, edits, video framesperceptual hash within a looser threshold, pHash and dHash must agree

Near-uniform images (flat screenshots, gradients, dark frames) are excluded from grouping because their perceptual hashes are meaningless. "Find similar" (context menu or F) does an ad-hoc perceptual search around one file.

10. Face / skin screening

Screening runs the YuNet face-detection neural network (a small bundled ONNX model, via OpenCV) over every thumbnail and records a face count, plus a skin-tone ratio (the fraction of pixels in a skin-colour range). Run it at ingest, or later with Run screening in the Screening section. These are triage signals to help you prioritise — they are not a classifier and make no judgement about content.

11. Known-hash matching & NSRL

A known-hash list is a set of hashes someone has already identified. GLEAPP checks each file's SHA-256 → SHA-1 → MD5 (exact) and then its pHash (perceptual, within a threshold) against:

  • case hash sets — imported into this case;
  • the global store — %LOCALAPPDATA%\GLEAPP\hashsets\, shared by every case, where large reference sets like the NSRL RDS live.

Set kinds:

knownnotable / bad. A hit shows the red HASH badge (purple STASH for your local hash stash) and, if the file is uncategorized and the set asserts a category, adopts it.
known-goodbenign (NSRL, OS/app files). A hit shows the grey NSRL badge, is auto-categorized Non-pertinent if uncategorized, and can be hidden with "Hide known-NSRL". Never overrides a category you set.
otherinformational only.

Importing a hash set into a case (e.g. a CyberTip)

Sidebar → Hash sets → Import hash set…. A file browser opens — pick the CyberTip file. GLEAPP fills a name in from the filename (edit it, e.g. CyberTip 12345678); pick Flag as notable (default — red HASH badge) or Mark as benign; click Import & flag. GLEAPP loads the hashes, re-checks every file, and jumps the grid to the matches. Each imported set is listed under the button with its entry / hit counts and an × to remove it (removing clears its flags). Use Show → Only: <name> to view one set's hits, or Any imported hash set for all of them; matches also appear in the report.

Accepted: a plain MD5 / SHA-1 / SHA-256 list (one per line, or hash,category), a CSV / TSV, a Project VIC JSON, or a CAID export. Matching is case-insensitive; a header row and blank lines are ignored.

Re-check (next to Import hash set…) re-runs matching against every loaded set — case sets, the global store, and the local hash stash — without a full reprocess.

The global store holds large reference sets like the NSRL RDS once, shared by every case, at %LOCALAPPDATA%\GLEAPP\hashsets\ (macOS ~/Library/Application Support/GLEAPP/hashsets/, Linux ~/.config/GLEAPP/hashsets/). Manage it from the sidebar: Hash sets → the "Reference data: … ▸" line opens a dialog that lists the imported sets (each with an ✕ to remove it) and an Add a set form. Accepts a SQLite .db, an NSRL .sql / delta, Project VIC JSON, CAID JSON, or a hash list. (The command line gleapp hashset --global … does the same, from a source install.)

Setting up the NSRL RDS

The National Software Reference Library Reference Data Set (RDS) is NIST's public catalogue of hashes of known software — operating systems, applications, their bundled files. Matching your evidence against it lets you eliminate the OS/app noise and concentrate on user content. GLEAPP does not ship it; you download it from NIST and import it once.

1. Download from NIST. https://www.nsrl.nist.gov/ → "Download RDS" (files at https://s3.amazonaws.com/rds.nsrl.nist.gov/RDS/). Four sets — Modern (desktop/laptop software — use this for computers), Android, iOS, and Legacy (pre-2000 software; skip unless you work vintage systems). Each set publishes a full SQLite .db once a year (RDS_YYYY.03.x_<set>.zip, tens of GB unzipped) and a quarterly delta (RDS_YYYY.MM.x_<set>_delta.zip, a <set>_delta.sql of changes since). Unzip what you download. Modern also offers a much smaller minimal database (distinct SHA-256 only) — for that, set Store to SHA-256 only in step 2.

2. First import (a full release). Hash sets → Reference data: … ▸ → Add a set: leave Full release selected, Choose… the unzipped .db, edit the Name if you like (e.g. NSRL Modern 2026.03.1), leave Treat matches as on Benign — NSRL / known-good and Store on MD5 only, click Import. It runs in the background (a full set is tens of millions of hashes) — progress shows under Hash sets, and you can keep working. Repeat for Android / iOS. The source .db can then be moved or deleted — GLEAPP never reads it again — except keep it as the base for the next delta.

3. Quarterly update (a delta). A delta is merged onto the previous full .db for the same set (the base is never modified). In Add a set choose Quarterly delta, pick the _delta.sql and the .db you kept, name it for the new quarter, Import. GLEAPP writes the merged .db next to the base. Remove the previous quarter's set with its ✕; keep the merged .db as the base for the next delta. Each year, start over from the new March full.

4. Use it. Open a case and click Re-check under Hash sets (or re-run Process). NSRL matches get the grey NSRL badge, are auto-categorized Non-pertinent if still uncategorized, and drop out of view when you tick Hide known-NSRL.

Deltas and SQLite: merging a delta needs SQLite. GLEAPP has a built-in fallback, so it works from the frozen app with nothing installed; if the sqlite3 command-line tool is on your PATH (or next to GLEAPP.exe) it is used instead and is faster on very large scripts.

12. Local hash stash

The local hash stash is your own reusable known-hash set, built from your casework: the MD5 hashes of every file you categorize 1 CAM, 2 Child Exploitative or 3 CGI/Animation, each stored with its category code. Match it against a new case and files you have already identified are re-flagged automatically.

It is its own file, separate from the NSRL / global store: %LOCALAPPDATA%\GLEAPP\hashsets\stash.gleapp — a small SQLite file (one stash table of md5, category, added_at, source). GLEAPP still ships no hash database and makes no content decision; the stash holds only hashes of files you categorized.

Creating / adding to it

  1. Work a case as normal — categorize files into codes 1, 2 and 3.
  2. Click Hash stash in the header. The panel shows how many of this case's files are eligible (category 1–3 with an MD5) and the current stash totals.
  3. Click Add this case's hashes to the stash. Each eligible MD5 is saved with its code and the case name as a source note. The stash file is created on first use.
  4. Repeat on other cases. Running Add again on the same case picks up anything categorized since; a hash already stashed under a different code keeps the more severe (lower) one.

Using it on other cases

  • Checked automatically during the known-hash matching stage of every case you process — nothing to import.
  • For a case processed before you stashed those hashes: open it and click Re-check known hashes (sidebar → Other).
  • A match shows the purple STASH badge. An uncategorized file adopts the stashed code; a category you already set is never overridden. Stash hits are checked before NSRL, so your own call wins.

Sharing it with other examiners

The Sharing section of the Hash stash panel:

Export a copy…writes a portable hash-stash-<date>.gleapp into %LOCALAPPDATA%\GLEAPP\hashsets\ — hand it to a colleague
Export CSV…same, as a md5,category,source CSV
Merge a colleague's stash…folds their .gleapp or .csv into yours; the more-severe code wins on any overlapping hash
Use a shared file…point GLEAPP at one stash file on a shared / network drive — the whole team reads and writes the same stash
Back to my ownrevert to your per-user stash.gleapp (the shared file is untouched)

The location can also be set with the GLEAPP_STASH_PATH environment variable (it wins over the panel setting). Clear stash… erases every entry across all cases and is not undoable.

Command line

gleapp stash                       # totals + file location
gleapp stash --add -c <case dir>    # add that case's category 1-3 MD5s
gleapp stash --export stash.gleapp # portable copy  (.csv also works)
gleapp stash --merge theirs.gleapp # fold in a colleague's stash
gleapp stash --set-path "\\nas\team\stash.gleapp"
gleapp stash --set-path ""         # back to the per-user default
gleapp stash --clear

13. Format handling

Beyond ordinary JPEG/PNG/GIF/WebP/BMP/TIFF and video, GLEAPP decodes:

  • HEIC / HEIF (iPhone photos) and TIFF / DNG — transcoded to JPEG for display.
  • iOS KTX GPU textures — SplashBoard app-switcher snapshots and other Apple textures, including LZFSE-compressed and AAPL chunked variants.
  • Extension-less app-cache files — content-sniffed by magic bytes (e.g. Snapchat's SCContent cache names files by hash with no suffix).
  • Snapchat LZC bundles — Zstandard containers; the embedded image or video is extracted to extracted/ and shown.

Native decoders that can crash on malformed data (video via OpenCV, GPU textures via the Rust decoder) run in isolated child processes, so one bad file can't take down the whole run — it's flagged with an error instead.

Some files a phone extraction or VIC export hands you contain no decodable media — the bytes just aren't there. GLEAPP labels each case plainly in the Error column instead of a raw decoder exception, and still records the MD5, VIC MediaID, size and metadata:

  • Incomplete carve by the source tool — the file name ends in _partial / _embedded_N: the tool that built the export tried to carve an image out of a parent file and got only its header. The real image is in the parent file — ingest that (e.g. the com.snap.file_manager_*_SCContent_ directory) and GLEAPP unpacks it.
  • Truncated PNG / JPEG — file header only, no image data.
  • Proprietary app-asset container — an app's own texture/filter format (e.g. AR make-up filters), not a standard image.
  • Snapchat streamed-video fragment / fragmented-MP4 init segment / MP4 media data with no header — a segmented download split across many files; reassembly is an upstream task.
  • Malformed HEIC/HEIF — declared and decoded image sizes disagree.
  • Audio-frame fragment / gzip-compressed web-cache data — not an image or video at all, despite the extension.

14. Reports & exports

Export report opens a dialog: choose a scope — all files, categorized only, uncategorized only, specific categories (tick exactly the ones you want, e.g. just CAM + Child Exploitative), or the current selection — and one or more formats:

HTML reporta self-contained page (thumbnails embedded) with your case header, a "Report contents" breakdown, and one card per image showing the fields you chose
CSVfull metadata, one row per file
JSONthe same data, structured; carries the case header too
KMZgeolocated media for Google Earth / mapping tools — a zipped KML with a thumbnail (or video key frame) bundled for every placemark, so clicking a pin shows the picture at its location
MD5 listone hash per row (also from the selection bar / right-click)

LAVA reporta project folder LAVA opens: the media, a location map for each geolocated file and an overview map drawn offline from the basemap you imported, the video key frames, and the artifact tables. Takes minutes rather than seconds, so it runs as a job and the bar at the bottom follows it

Filesystem / ingest times in the HTML and CSV are rendered in the case's timezone (section 3) with the abbreviation shown (e.g. 2024-07-01 11:00 CDT); the HTML header states which zone. Captured (EXIF) is left as recorded; JSON keeps raw epoch seconds (UTC).

HTML report options

When HTML report is ticked the dialog shows:

  • Report header — Agency, Case number, Item number, Examiner, free-text Notes, and an Agency logo (pick an image; it's embedded in the report). These print as a banner across the top of the report and are saved with the case, so they pre-fill next time — fill them once per case.
  • Fields under each image — tick the metadata you want beneath every thumbnail: file name, original name, path, device path, captured date, file-modified / ingested dates, MD5 / SHA-1 / SHA-256 / pHash, dimensions, size, duration, camera, GPS, category, tags, notes, faces, skin ratio, source, MIME type, VIC MediaID, known-hash, error. The default is file name, captured date, MD5; your selection is remembered per case. Fields with no value for a given file are simply left out of that card.

The HTML report is grouped by category: a "Jump to section" index at the top links to each category's section — CAM, Child Exploitative, and so on — and every section header has a back-to-top link. Each card's metadata starts collapsed (click the file name, or "expand all"). A control bar above the first section has two switches: Blur images (on by default — hover a thumbnail for a clear look) and Dark mode; both remember your choice per browser. Printing shows every card's metadata and unblurred images in light mode.

Media (dialog checkboxes, on by default, saved with the case):

  • Embed full-size images — each image goes in downscaled to ≤ 2000 px; click a thumbnail to open it full size in a new tab. HEIC/HEIF included.
  • Embed playable videos — each video file is added to the report; a play triangle marks video cards and clicking opens the video playing in a new tab. This is what makes the report large — untick it (or "full-size images") for a lean thumbnails-only report.

The report stays a single self-contained file either way.

A Report contents breakdown near the top gives the file count for the report's scope, split by type and by category (with a percentage and a colour key matching your categories), a thin composition bar, known-hash matches, and the case total. Outputs land in the case's reports/ folder; scoped exports get a filename suffix.

15. Autosave & snapshots

Every category, review, tag and note change is committed immediately (SQLite WAL). The header shows "All changes saved · HH:MM" / "Saving…" / a retry prompt on failure. In the background, a full timestamped copy of case.gleapp is snapshotted to backups/ roughly every 10 minutes while there are unsaved-since-last-snapshot edits, and always when you close or switch cases. The newest 20 snapshots are kept.

The Snapshots header button opens a panel listing every snapshot with its date, label (auto, manual, or your text) and size:

  • Save snapshot now — makes one on demand, with an optional label.
  • Restore — replaces the live case with the selected snapshot. The current state is written to a pre-restore snapshot first, so a restore is itself undoable; the case then reloads. Restore is blocked while a job is running.

16. Reprocessing

  • Retry failed files — re-run processing on files with an error (after a fix, or a transient failure). Shows how many were recovered.
  • Re-scan for duplicates — rebuild groupings only.
  • Re-check known hashes — rebuild hash-set matches only.
  • Run screening — face/skin pass only.

Each reports progress next to its own button. A full reprocess is available from the command line (gleapp process --force).

18. Data & privacy

GLEAPP runs entirely on your machine with no network access; even the maps are drawn from a basemap file you import (section 19), never from a tile server. The evidence you ingest is only ever read; all output is written inside the case folder and the per-user config / hash store under %APPDATA% and %LOCALAPPDATA%. Examiner actions (categorize, snapshot, import, re-match, VIC import, hash-stash add / merge / clear) are recorded in the case's audit log for defensibility. GLEAPP does not bundle, and cannot identify, any illegal content — it identifies known files (via hashes you supply, including your own local hash stash) and surfaces signals; the categorization is always your professional judgement.

The local hash stash (section 12) holds MD5 hash values only — no file content, names or paths — of files you categorized 1–3, and never leaves your machine unless you Export it or point it at a shared location.

19. Maps (offline basemaps)

GLEAPP ships no map data and fetches none, so a subject's coordinates never reach a server somebody else runs. To see geolocated files on a map, import a basemap file once with the Maps button in the header; GLEAPP copies it under its data folder, records its SHA-256, and draws maps from it entirely offline. The details pane then shows a map for any file with GPS (plus a Copy button for the coordinates), and Show current filter on the map plots every geolocated file matching your filters; click a marker for its thumbnail and a Details button. The HTML report also draws its own maps from the basemap and embeds them: a Locations overview of every geolocated file near the top, and a small locator map on each geolocated file. Those images are baked into the report file, so it stays self-contained and offline; the summary names the basemap and its hash so a reader can obtain the same file and see the same map. Use --no-maps (or the Export dialog) to leave the report maps out.

Two file types are accepted. A .pmtiles region is the recommended one: install the pmtiles tool from github.com/protomaps/go-pmtiles/releases, pick a recent Protomaps planet build (https://build.protomaps.com/YYYYMMDD.pmtiles), and cut your area with a bounding box, west, south, east, north in decimal degrees, for example pmtiles extract https://build.protomaps.com/20260902.pmtiles dc.pmtiles --bbox=-77.12,38.79,-76.90,38.99. That reads only the tiles inside the box; a metro area is tens of megabytes and a small country under a hundred, at street-level detail. A raster .mbtiles made with QGIS or MapTiler Desktop also works, for a map you already have; vector MBTiles are not accepted. The same actions exist on the command line as gleapp maps list | import | remove | use | extract.

The Protomaps builds are OpenStreetMap data under the ODbL, and the map shows the "© OpenStreetMap contributors" credit that licence asks for. It is shown as plain text rather than a link, because a link would be the one outbound address on the page.

Face / skin screening (section 10)

  • YuNet — the bundled face detector (face_detection_yunet_2023mar.onnx, ~230 KB): a lightweight face-detection CNN by Shiqi Yu, Wei Wu and Yuantao Feng, distributed through the OpenCV Zoo project (MIT). Run on the CPU via OpenCV's DNN module.
  • Haar cascade fallback (haarcascade_frontalface_default.xml) — trained by Rainer Lienhart; ships inside OpenCV.
  • Skin-tone ratio uses no model — a plain HSV + YCrCb colour-range measurement, the classic approach from the skin-detection literature (e.g. Kovač, Peer & Solina, 2003).

Similarity search & de-duplication (section 9)

Find similar, visual-duplicate stacking (≈ N) and near-duplicate clusters are built on ImageHash's perceptual hashes. The perceptual-hash / pHash idea itself is owed to Neal Krawetz (“Looks Like It”) and Christoph Zauner (pHash.org). The rest — Hamming-distance ranking, the LSH banding that keeps near-dup clustering out of O(n²), and per-key-frame video matching — is GLEAPP's own code, no extra library.

Data standards & reference data (you supply these — none are bundled)

  • Project VIC — Project VIC International. GLEAPP's locked category scheme (codes 0–5) is the Project VIC 2.0 (US) VICS data model, and GLEAPP reads and writes the Project VIC JSON case format.
  • NSRL RDS — the National Software Reference Library Reference Data Set, produced by NIST (public domain). GLEAPP imports it; it does not include it.
  • CAID — CAID-style CSV hash-list handling follows the UK Home Office Child Abuse Image Database export layout.
